## The table

`hrn route from-eval f353a` (margin 0.05) produced the rows below, saved to `~/.hrn/route.json`
on the machine that ran the eval and copied to [`route-2026-10-15.json`](route-2026-10-15.json).
They replace yesterday's rows for the same five purposes.

| purpose | backend | model | effort | why |
|---|---|---|---|---|
| debug | codex | gpt-6.1-sol | medium | Sol, Sonnet and Haiku all 3/3; codex has no cost data, so it ranks cheapest |
| implement | codex | gpt-6.1-sol | medium | Sol, Sonnet and Haiku all 6/6; same tie-break |
| research | codex | gpt-6.1-sol | medium | the only variant at 3/3 |
| test | codex | gpt-6-luna | low | all four at 3/3; lowest effort among the no-cost variants |
| unknown | codex | gpt-6-luna | low | all four at 3/3; same |

**Read this before relying on it.** The rules rank by pass rate within the margin, then by
cost. Codex records no cost, which the eval table stores as zero, so a codex variant that passed
beats any Claude variant that also passed, whatever Claude cost. Sonnet at medium effort tied
Sol on implement, debug, test and unknown and would appear in the table only where Sol failed,
which it never did here. Until hrn carries a codex price (noted on harness #297), the table
answers "which no-cost variant passed" and ranks Claude only against other Claude variants. The
research row is the one place the evidence is unambiguous: Sol passed all three, every other
variant failed at least once. No row exists for `review`, `refactor`, `plan` or `ops`; the suite
has no task of those purposes, and `hrn route` keeps the backend default for a missing row.
